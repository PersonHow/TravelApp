# Travel App 競品分析與定位評估

最後更新：2026-11-18

**結論摘要：** 原本認定的三個差異化賣點，經查證後推翻兩個、修正一個。目前真正站得住的是「整合性」與「資料穩定性」兩項品質條件，但都尚未驗證使用者是否感知得到。最大的市場痛點（長輩抗拒下載註冊）與本專案的 LINE-first 路線完全對齊，但目前**連分享連結邀請都還沒有**，該痛點尚未被現有流程解決。

### 市場標配（做了不算優勢）

1. 按日時間軸排程與拖拉排序
2. 地圖釘選與點對點交通時間預估
3. 分享連結／邀請旅伴共同編輯
4. 備註與訂位代號欄位
5. **基礎 AI 行程生成**（2024–2026 年起已成標配）

> 第 5 項要特別認清：「AI 幫我排行程」在 2026 年不是賣點。

### 使用者痛點（市場普遍做不好）

| # | 痛點 | 現況缺陷 |
|---|---|---|
| 1 | 長輩／被動旅伴抗拒下載註冊 | 主揪最後仍是匯出 PDF 或截圖丟 LINE 群組，行程一改就不同步 |
| 2 | 只有主揪一人在排，前期決策癱瘓 | 現有 App 都假設「大家已討論好」，缺前期匿名預算收集與輕量投票 |
| 3 | 分流合流排程不友善 | 幾乎全是單一線性時間軸，無法清楚表達同時段兩組人不同行程 |
| 4 | 旅途中即時應變太笨重 | 改動結構化行程表牽一髮動全身，多數團隊第 2 天就放棄更新 |
| 5 | 以家庭為單位的權重分帳 | 多半只支援全體均分或逐一手動輸入 |

**痛點 5 的修正：** 原判斷「市場上分帳只能均分」已被推翻——Splitwise 支援份數與比例分攤，Wanderlog 支援依帳目自訂參與分攤者。真正待驗證的是「**以家庭為單位**設定份數，是否比現有按人分攤明顯方便」。（此項由 Codex 提出，本文未獨立驗證該兩款產品的實際行為。）

## 定位評估

### 被推翻的賣點

| 原本認定 | 查證結果 |
|---|---|
| **旅遊短句是獨有功能** | ❌ **不成立。** GoJa 已提供群組共用日文短句含羅馬拼音與發音朗讀；Japan Trip Go、Pack for Japan 亦有羅馬拼音短句庫 |
| **AI 審核專家鏈保證行程品質** | ⚠️ **過度宣稱。** `aiPlanService.generate` 確實是「規劃 → 審核 → 修一輪」，但**修完不再審**（程式註解自述「最多一輪，控制成本」），且審核只看文字脈絡，未實際查證交通與營業時間。只能描述為「草稿經過第二輪檢查」 |
| **飯店大眾運輸路線（飯店 → 景點）** | ⚠️ **方向講反了。** 實際端點是 `GET /trips/:id/hotels/:hotelId/transit-route?origin=…`，查的是**出發地 → 飯店**（例如關西機場 → 飯店），用途是抵達日交通，不是住宿期間的景點往返。競品是否將同等功能鎖在付費方案，亦未能證實 |

### 目前站得住的條件

兩項皆屬「品質證據」而非行銷賣點，且**尚未驗證使用者是否感知得到**：

1. **單一 Trip 聚合全部脈絡** — 住宿、航班、每日安排、記帳、行李清單、旅遊短句都掛在同一個 Trip 底下，AI 規劃時會讀入航班與住宿避開衝突。降低切換資料的負擔，但整合式旅遊 App 已存在。
2. **活動保留地點快照** — `DayActivity` 儲存排程當下的 `placeId` 與經緯度，外部景點資料變動不會改寫既有行程。

**授權模型紮實**（`assertAccess` / `assertMember` / `assertRole`＋巢狀資源隸屬驗證，拿 A 行程權限改 B 行程回 404）適合作為品質證據，但競品可能也具備，且使用者難以從功能介紹感知，不宜單獨宣稱為差異化。

### 已確認的缺口

| 痛點 | 本專案現況 |
|---|---|
| 1 長輩不下載 | **roadmap 核心方向（LINE-first），但未實作。** 目前家庭邀請是用 email 加入**已註冊使用者**（`familyService`），連分享連結共編都沒有 |
| 2 前期投票 | 完全沒有。無候選池、無投票、無任務指派 |
| 3 分流合流 | 無分組概念，與所有競品同一弱點（詳見下節） |
| 4 即時應變 | 規劃為 AI 第四批，未動工 |
| 5 權重分帳 | `Expense` 只有 `amount` ＋可空的 `payerId`，無應分攤者、應付金額或結算 |

## 兩項判斷的修正紀錄

### 「家庭權重分帳是成本最低的機會」— 不成立

`Expense` 模型簡單代表要處理的既有邏輯少，但也代表**幾乎沒有可沿用的分帳基礎**。若要實作，至少牽動：

- `POST`／`PUT`／`DELETE /api/trips/:id/expenses` 的輸入驗證與寫入；`GET /api/trips/:id` 是否回傳分攤結果。現有建立 schema 對未知欄位嚴格驗證，不能直接塞權重欄位
- 前端型別、`services/`、`ExpenseFormModal` 與記帳頁：選參與者、輸入份數、顯示各方應付
- 資料遷移：舊帳目不能無依據視為全員均分；`payerId` 可為空時無法計算完整結算；整數金額的餘數分配規則待定
- **「家庭」的定義要先釐清** — 目前一個 Trip 屬於一個 Family，`FamilyMember` 皆為已註冊 User，**沒有「行程內多個家庭」或未註冊旅客的模型**。不能直接把現有 Family 當分帳子群
- `expenses.test.ts` 需擴充：份數與參與者、餘數加總、編輯刪除、舊資料與未指定付款人的行為

**建議的先行驗證：** 讓目標家庭先用既有工具按人輸入份數，觀察他們是否反覆需要把多人合成一個家庭、哪一步最麻煩，再界定最小實作。

### 「分流合流必須改核心資料模型」— 說得太強

`DayActivity` 有開始／結束時間與排序，**沒有時間重疊的唯一限制**，`tripDayService` 建立活動時也未檢查同時段衝突。資料層本來就存得下兩筆同時段活動，只是沒有機器可辨識的分組或參與者欄位。

**低成本驗證做法：** 用既有活動標題或備註人工標記「A 組」「B 組」，各建同時段活動，再建一筆共同集合活動。不需改 schema，可用來測試需求是否真的存在。限制是無法依成員篩選、驗證合流或分別計算交通。

**已知架構衝突：** `aiPlanService` 的排程脈絡會要求新活動避開既有安排，`reviewTrip` prompt 把時間重疊視為衝突。即使資料存得下平行活動，AI 仍不理解分組，日後正式支援時必須處理。

## 下一步建議

依「市場痛點嚴重度 × 與現有架構的契合度」排序：

1. **分享連結邀請共編** — 痛點 1 是市場第一痛點，也是 LINE-first 路線的前置條件。目前連最低限度都沒有
2. **確認 transit-route 的實際價值** — 先在日本常用機場與飯店實測能否穩定查到路線，再決定要不要擴充成雙向
3. **分流合流的人工標記驗證** — 零成本，先確認需求真偽
4. **權重分帳** — 先做使用者觀察，不要直接進實作
